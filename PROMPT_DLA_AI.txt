Jesteś elitarnym inżynierem oprogramowania i głównym architektem silnika budowania w Minecraft 1.21.4 (Mojang mappings, Fabric, mechanika Baritone / Litematica).
Twoim zadaniem jest przeanalizowanie, naprawienie i wdrożenie kompletnych poprawek do kodu silnika autonomicznego budowania (`AstraSchematicManager.java`, `AstraSchematic.java`, `SchematicHologramRenderer.java`).

Poniżej znajduje się pełna analiza zachowania bota na podstawie zrzutów ekranu ze świata gry, dogłębna diagnoza techniczna 5 źródeł błędów oraz dokładny kod naprawczy.

---

## 1. ANALIZA ZRZUTÓW EKRANU I OBJAWÓW W GRZE

1. **Zrzut ekranu 1 (Układ bazowy):**
   - Bot rozpoczyna budowę dolnej warstwy automatycznej farmy trzciny cukrowej.
   - Postawił rząd bloków ziemi (5 bloków dirtu), obok znajduje się wyznaczona w schemacie rynna wodna (niebieskie obrysy wokseli wody).
   - W ekwipunku gracza znajduje się wiadro z wodą (`Items.WATER_BUCKET`).

2. **Zrzut ekranu 2 (Moment zbugowania się bota):**
   - Gracz stoi w 1-kratkowej rynnie z wodą tuż obok posadzonej trzciny cukrowej (`SugarCaneBlock`). Wiadro wody zostało zużyte (w hotbarze pojawiło się puste wiadro `Items.BUCKET`).
   - Wokół wody pojawiły się gigantyczne, jaskrawoczerwone półprzezroczyste prostopadłościany (`PlacementStatus.WRONG_BLOCK`).
   - **Kamera bota gwałtownie trzęsie się i drży w osiach Yaw/Pitch (20 razy na sekundę), bot nie może się ruszyć (0.0 bps) i całkowicie zamarza w miejscu.**
   - Warstwa tłoków (`PistonBaseBlock`) i obserwatorów (`ObserverBlock`) za trzciną nigdy nie zostaje postawiona.

## 2. DOKŁADNA DIAGNOZA TECHNICZNA (5 PRZYCZYN W KODZIE)

### PRZYCZYNA 1: Pętla wojny o rotację kamery między niszczeniem bloku a Baritone (Gwałtowne drżenie kamery)
- W metodzie `processPostInteractOrBreakWrongPass`:
  Gdy wykryto `wrongBlockPos`, bot żąda obrotu kamery w stronę bloku:
  `rotationController.requestRotation(bestBreakRot, AimPriority.PLACEMENT_RAYCAST, 3);`
  Następnie w tym samym ticku wykonuje raycast `level.clip(...)`.
- Jeśli raycast w ticku 0 jeszcze nie trafił w `wrongBlockPos` (np. rotacja potrzebuje 1 ticku na płynne wygładzenie, kąt jest minimalnie odchylony lub w celu znajduje się woda):
  Kod natychmiast anulował niszczenie (`stopDestroyBlock`), zerował stan i **zwracał `false`**!
- Zwrócenie `false` powodowało, że w tym samym ticku silnik przechodził do kolejnych kroków:
  1. `processFastSynchronizedPlacement` – żądał innej rotacji do postawienia kolejnego bloku.
  2. `executeNavigationAndBridgingPass` – uruchamiał nawigację Baritone (`setGoalAndPath`), która brutalnie przestawiała kąty kamery na węzeł ścieżki.
- W następnym ticku `processPostInteractOrBreakWrongPass` znowu wykrywał `wrongBlockPos`, anulował Baritone (`cancelEverything()`) i obracał głowę z powrotem.
- **Efekt:** W każdym ticku głowa gracza była szarpana między dwoma różnymi kątami – powstał efekt „drżącej kamery”.

### PRZYCZYNA 2: Paraliż ruchowy (Ledge Sneak) w 1-kratkowej wodzie
- W metodzie `enforceGlobalLedgeSafety`:
  Gdy gracz stoi w 1-kratkowej rynnie z wodą, `feetPos = player.blockPosition()` zawiera wodę, a `belowPos = feetPos.below()` to twarda ziemia pod wodą.
- Warunek `if (!belowState.getFluidState().isEmpty())` sprawdzał stan podłoża `belowPos` zamiast stóp gracza `feetPos`!
- W efekcie silnik uznawał, że gracz stoi na krawędzi niebezpiecznej przepaści i wymuszał permanentne kucanie: `setPlayerSneak(player, true)`.
- **W mechanice silnika Minecraft kucanie w wodzie uniemożliwia podskoczenie i wejście na sąsiedni pełny blok (blokuje step-up). Bot staje się fizycznie uwięziony na dnie rynny wodnej.**

### PRZYCZYNA 3: Odrzucanie płytkiej wody w `isStandablePosition`
- W klasie `SchematicBuildNavigator.isStandablePosition`:
  ```java
  if (!feetState.getFluidState().isEmpty() || !headState.getFluidState().isEmpty()) {
      return false;
  }
  ```
- Warunek ten bezwzględnie odrzucał każde pole, na którym na poziomie stóp (`feetState`) znajduje się woda, nawet jeśli pod spodem jest twardy blok ziemi, a głowa gracza jest w powietrzu!
- W rezultacie:
  - Gdy gracz wpadł do rynny, silnik uznawał jego pozycję za nielegalną.
  - Metody `findReachableStandingPositions` oraz `findNearestStandableToTarget` odrzucały wszystkie pozycje w rynnie farmy.
  - Nawigacja zwracała `REQUIRES_BRIDGE_OR_SCAFFOLD`, zliczając `taskStuckTicks` aż do zamrożenia bota.

### PRZYCZYNA 4: Przedwczesny `break` w `ScaffoldingSolver.findNextScaffoldTask`
- W metodzie `findNextScaffoldTask`:
  ```java
  for (BlockPos stepPos : cachedSupportChain) {
      if (stepPos.equals(floatingTargetPos)) {
          break; // BŁĄD! Przerywało pętlę ZANIM sprawdzono stepPos!
      }
      BlockState current = level.getBlockState(stepPos);
      ...
  }
  ```
- Gdy wyznaczono rusztowanie pod brakujące stanowisko stania za tłokami (`axialStandGround`), `floatingTargetPos` było ostatnim (często jedynym) blokiem łańcucha.
- Przez `break` blok ten **nigdy nie zostawał wytypowany do postawienia**, więc bot nie mógł zbudować podestu, aby wejść za trzcinę i postawić tłoki.

### PRZYCZYNA 5: Płynąca woda oznaczana jako czerwony `WRONG_BLOCK`
- Po rozlaniu wody z wiaderka ciecz rozlewa się na sąsiednie kratki powietrza.
- W `SchematicHologramRenderer.evaluatePlacementStatus`:
  Dla sąsiednich kratek schemat miał stan `AIR`, a w świecie pojawiła się woda (`Blocks.WATER`).
  Metoda nie ignorowała cieczy w pustej przestrzeni i zwracała `PlacementStatus.WRONG_BLOCK`.
- Z kolei w `DirectionalStateSolver.requiresBreakAndReplace` brakowało wykluczenia bloków cieczy (`LiquidBlock`), przez co bot próbował niszczyć rozlaną wodę kilofem! Ponieważ raycast `ClipContext.Fluid.NONE` przenika przez wodę, cel nigdy nie trafiał w blok, potęgując drżenie kamery.

### C. W pliku `SchematicHologramRenderer.java`:
Ignorowanie rozlanej wody w pustych przestrzeniach w `evaluatePlacementStatus` (likwidacja fałszywych czerwonych obrysów):
```java
    private PlacementStatus evaluatePlacementStatus(Level level, BlockPos pos, BlockState worldState, BlockState targetState) {
        if (targetState.isAir() && worldState.isAir()) {
            return PlacementStatus.EMPTY_IGNORE;
        }
        if (targetState.isAir() && (worldState.getBlock() instanceof net.minecraft.world.level.block.LiquidBlock || !worldState.getFluidState().isEmpty())) {
            return PlacementStatus.EMPTY_IGNORE;
        }
        if (AstraSchematic.matchesStateSemantics(level, pos, worldState, targetState)) {
            return PlacementStatus.CORRECT;
        }
        if (worldState.isAir()) {
            return PlacementStatus.MISSING;
        }
        if (worldState.is(targetState.getBlock())) {
            return PlacementStatus.STATE_MISMATCH;
        }
        return PlacementStatus.WRONG_BLOCK;
    }
```
